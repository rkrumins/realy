# Developer guide

## Repository layout

| Path | What |
|---|---|
| `contracts/` | the source of truth: protobuf (`proto/`), feature DSL (`features/feature_schema.yaml`), topics (`kafka/topics.yaml`), ClickHouse DDL (generated) and Redis layout |
| `rules/` | CEL rule sets (`baseline.yaml`) |
| `scenarios/` | scenario packs (YAML, [schema](reference/scenario-schema.md)) |
| `java/` | Gradle multi-project. `common` (Kafka props, clock, admin HTTP), `scoring-core` (features, rules, model client, orchestrator), `scoring-gateway`, `flink-job`, `mock-model-server`, `load-emitter`, `contracts` (generated stubs) |
| `python/realy/` | `world` / `gen` (synthetic data), `emit` / `collect` (driver), `runner`, `report`, `verify`, `budget`, `features` / `scoring` (reference implementations), `train`, `control` (console API), `codegen` / `k8s` / `docsgen` (generators) |
| `ui/` | console: React 19 + TypeScript + Vite + Tailwind CSS v4 |
| `deploy/` | `docker/Dockerfile`, `compose/`, `k8s/` (Kustomize), Prometheus/Grafana config |
| `models/` | proxy-model weights (mock) and Triton model repositories (`realy train`) |
| `docs/` | these docs; `docs/reference/` is generated |

## Host toolchain (optional)

Docker alone builds and runs everything. For a faster inner loop you need JDK 21, Python 3.11 or
later (3.13 recommended) and Node 22:

```bash
make dev-venv        # .venv with realy[control,train,fast,dev]
make dev-build       # Gradle: service distributions + Flink job jar
make up              # the stack in Docker (the host tools talk to it on localhost)
make test            # Java (JUnit + Flink MiniCluster on RocksDB) + Python (pytest)
```

| Loop | Command | Notes |
|---|---|---|
| UI | `make dev-ui` | Vite on :5173 with hot reload. It proxies `/api` and the live WebSocket to :8090: the console container, or `make dev-console` |
| Console API | `make dev-console` | FastAPI on the host against the Docker services. Stop the console container first (`docker compose stop console`) to free :8090 |
| Java service | `make dev-build`, then `docker compose up -d --build gateway` | or run `java/scoring-gateway/build/install/scoring-gateway/bin/scoring-gateway` on the host with `KAFKA_BOOTSTRAP=localhost:9092 REDIS_URI=redis://localhost:6379 MODEL_TARGET=localhost:8001` |
| Flink job | `make flink-reload` | rebuilds the flink image. The next run submits the new jar, and the savepoint is reused when operator uids match |
| UI tests | `cd ui && npm test` | vitest: latency-distribution math, YAML-to-form sync |

## Generated files

Edit sources, never outputs. `make codegen` runs every generator; CI fails on drift.

| Generator | From | To |
|---|---|---|
| `scripts/gen-proto-python.sh` | `contracts/proto` | `python/realy/**/v1/*_pb2.py` (Java stubs are generated by Gradle) |
| `python -m realy.codegen` | proto + feature schema | `contracts/storage/clickhouse/*.sql` |
| `python -m realy.k8s` | contracts, `deploy/compose/kafka/create-topics.sh` | `deploy/k8s/**/generated/*` |
| `python -m realy.docsgen` | scenario models, control.proto, CLI, OpenAPI, feature schema, rules, topics, scenarios | `docs/reference/*.md` |

## Recipes

### Add a feature

1. Add one line to `contracts/features/feature_schema.yaml`, for example:
   `- { name: card_count_10m, source: stream, entity: card, agg: count, window: 10m, granularity: 10s }`.
   * **Position** is the model-tensor index, so append new features.
   * **Aggregations:** `count`, `sum`, `max`, `avg`, `distinct`, `novel`, `time_since_last`, `geo_speed_kmh`.
   * **`filter`** names a CEL predicate from `filters:`.
2. `make codegen`. The ClickHouse decision columns and the docs follow automatically.
3. Nothing else for stream and profile features: the Java `EntityAggregator` and the Python
   reference engine (`python/realy/features/engine.py`) are both driven by the schema.
   A **derived** feature additionally needs the same function in
   `java/scoring-core/.../features/DerivedFeatures.java` and `python/realy/features/derived.py`.
4. `make test` (Java `EntityAggregatorTest`, Python feature engine tests).
5. Retrain the proxy model, because the tensor width changed: `realy train --run <run>`.
6. Run `flink-inline-smoke` and then `realy verify <run>`. This is the Java-vs-Python parity proof:
   the verifier recomputes every served feature with the Python reference engine. It demands exact
   equality for customer and card features and reports the agreement rate for shared entities.

### Add or change a rule

Edit `rules/baseline.yaml`, or add `rules/<name>.yaml` and set `rules: <name>` in a scenario.
* Rules are CEL over `f` (features as doubles: write `3.0`, not `3`) and `event` (enums by name).
* Every run sends the rule set to the services (`rule_set_yaml` in `ScoringConfig`), so no rebuild
  is needed.
* `realy verify` re-evaluates every decision with the Python CEL implementation and reports any
  mismatch. Precedence is documented in the [rule catalog](reference/rules.md).

### Add a fraud typology

1. Add the value to `FraudType` in `contracts/proto/realy/payments/v1/label.proto`, then `make codegen`.
2. Add it to `FraudKind` in `python/realy/scenario.py`, and to `FRAUD_TYPE` and the default `mix`.
3. Implement `CampaignEngine._<kind>(self, T, p)` in `python/realy/gen/campaigns.py`. It returns
   event columns with ground-truth label columns (`self.label_cols(...)`); copy the shape of
   `_card_testing`. Parameters come from `fraud.campaigns[].params`.
4. Add a scenario pack in `scenarios/` that runs a campaign of the new kind, and rules that catch it.
5. `make test`. `python/tests/test_gen.py` checks determinism and that each typology trips its rules; add a case for the new one.

### Add a topology

A topology decides which component consumes `payments.events.raw` and produces decisions:

1. Add the name to `Topology` in `python/realy/scenario.py`.
2. **Wiring:** `python/realy/runner/run.py` switches gateway Kafka ingress via `bench.control`, and
   `python/realy/runner/flink.py` chooses the Flink job mode (`features` for the gateway topologies,
   `inline` / `both` for flink-inline; `echo-kafka` leaves Flink alone because the *gateway* echoes).
   The job's own `--mode echo` is an instrument-calibration mode no bundled topology uses.
3. **Live map:** add nodes and edges to `python/realy/control/topology.py` (each with a metric
   reference to a `bench.metrics` source and counter or stage), and a diagram to the UI's topology
   picker (`ui/src/lib/topology.ts`).
4. Keep the emitter and collector unchanged. Every topology must emit `DecisionRecord`s with spans
   so reports stay comparable.

### Add a console page or endpoint

* **API:** add a router under `python/realy/control/`, include it in `app.py`, and add a test in
  `python/tests/`. Endpoints appear in the generated [HTTP API reference](reference/http-api.md).
* **UI:**
  * add the page under `ui/src/pages/`, the route in `ui/src/App.tsx` and the nav entry in
    `ui/src/components/layout/nav.ts`;
  * API types live in `ui/src/lib/types.ts`, and data fetching uses TanStack Query hooks in
    `ui/src/lib/api.ts`;
  * the components in `ui/src/components/ui/` are the design system; reuse them.

## Tests

| Suite | Where | Covers |
|---|---|---|
| Java | `java/*/src/test` | feature aggregators, CEL rule sets, orchestrator deadlines and fallbacks, latency models, mock-model capacity model, Flink MiniCluster end to end on RocksDB |
| Python | `python/tests` | world and generator determinism, fraud typologies tripping their rules, feature engine, budget Monte Carlo, report, console API (auth, env, explorer, docs, topology, SPA fallback) |
| Parity (runtime) | `realy verify <run>` | Java vs Python features and CEL decisions on every event of a real run, plus ClickHouse audit completeness |
| UI | `ui/src/**/*.test.ts` | distribution math, YAML-to-form round trips |
| End to end | CI `e2e` job, manual `workflow_dispatch` | `make up`, then `smoke`, `flink-inline-smoke` and `realy verify` inside the console container |

## Releasing images

```bash
make images
for i in scoring-gateway mock-model-server flink console; do
  docker tag realy/$i:dev REGISTRY/realy/$i:vX.Y.Z && docker push REGISTRY/realy/$i:vX.Y.Z; done
```

Then update the `images:` block of the overlay you deploy ([deployment-kubernetes.md](deployment-kubernetes.md)).
